# Design: source-health

## Purpose

Every source's health is decided once, by the daemon, from what its fetches actually served, stored with the evidence it was decided from, and shown on every screen as stored; a failing source is retried less often instead of being switched off; and the operator is told on the main screen when a source needs them, until they fix, remove or keep it.

## Form

One stored record per source, written by the daemon, read by everyone.

1. Schema (migration 4 in daemon/src/prismis_daemon/database.py, joining _MIGRATIONS at line 143, and the same columns in schema.sql's sources table at line 20). Additive columns on sources, each added only when absent like _migrate_3_source_naughty: next_fetch_at TEXT NULL (the earliest time a failing source is fetched again; NULL means every cycle), entries_served INTEGER NULL (how many entries the last successful fetch served; NULL when the fetcher could not say), newest_item_at TEXT NULL (the newest item time the daemon has seen for the source, never lowered), health TEXT NULL CHECK(health IN ('healthy','broken','empty','dormant')) (NULL until first classified), kept_health TEXT NULL (the health the operator kept), kept_at TEXT NULL, and attention INTEGER NOT NULL DEFAULT 0. A trigger AFTER UPDATE OF active, health, kept_health, beside update_sources_timestamp (schema.sql line 115), sets attention = (active = 1 AND health IN ('broken','empty','dormant') AND (kept_health IS NULL OR kept_health != health)), so the warning rule has one definition, in the schema, whatever writes the row. error_count keeps its meaning, consecutive failed fetches, and is the backoff counter. The migration then (a) sets active = 1 on exactly the rows with active = 0 AND error_count >= 5, which only the five-strike rule can have written (storage.py line 1450: resume zeroes error_count, and a paused source is never fetched), and (b) backfills newest_item_at from MAX(content.published_at) per source.

2. Fetch report. A FetchedItems class (a list of ContentItem carrying served: int | None and newest_entry_at: datetime | None) in daemon/src/prismis_daemon/models.py is what every fetcher's fetch_content returns, so the 39 test call sites that treat the result as a list are unchanged. RSS (fetchers/rss.py line 145) reports len(feed.entries) and the newest published or updated date over every entry, before the max-items slice and the lookback filter. Reddit reports the listing entries it walked and the newest created_utc among them. YouTube reports the videos discovery returned and their newest upload time, and served None when discovery returns nothing, because a date-filtered discovery (youtube.py line 235) cannot tell a channel with no videos from one with none recent. File reports served 1 when it read a non-empty text body (unchanged or not) and 0 for an empty or non-text body, with no newest_entry_at. An HTTP error still raises (rss.py line 127), so a 404 stays a failed fetch, never an empty feed. Every newest time is clamped to now.

3. Backoff, in DaemonOrchestrator.run_once (orchestrator.py line 572). The orchestrator takes an injectable clock (default UTC now). The cycle reads its start time once. A source is fetched this cycle when next_fetch_at is NULL or falls before the cycle start plus half the fetch interval, so a retry lands on the cycle nearest its due time and the scheduler's start-time jitter can never push it a whole cycle late; every other active source is skipped with a console line naming when it is next due. After a fetch, Storage.record_fetch_success(source_id, served, newest_entry_at, at) sets error_count 0, last_error NULL, last_fetched_at, next_fetch_at NULL, entries_served, and raises newest_item_at to newest_entry_at; Storage.record_fetch_failure(source_id, error, at, fetch_interval) increments error_count to n, sets last_error, and sets next_fetch_at = cycle start + min(fetch_interval x 2^(n-1), 1440 minutes). Each newly stored item raises newest_item_at to its published_at (an undated RSS entry carries its fetch time, rss.py; a file change carries the time it was seen, file.py), which covers sources whose served entries carry no date. update_source_fetch_status and its five-strike UPDATE (storage.py line 1312) are deleted; nothing in the daemon writes active.

4. Classification, in a new daemon/src/prismis_daemon/source_health.py beside drift.py: classify(row, now, fetch_interval) -> health | None, pure, and the constants DORMANT_DAYS = 90 and BACKOFF_CAP_MINUTES = 1440. broken_after(fetch_interval) is the smallest n with fetch_interval x 2^(n-1) >= 1440, the failure whose wait first reaches the daily cap (5 at 120 minutes, 7 at the default 30). Rules in order: error_count >= broken_after -> broken; entries_served == 0 -> empty; newest_item_at older than 90 days, or newest_item_at NULL and created_at older than 90 days -> dormant; a source that has fetched successfully at least once -> healthy; otherwise NULL (never fetched). A failure count below broken_after changes nothing: the source keeps the health its last successful fetch earned, and its failures show as evidence. At the end of run_once, after the drift check and under the same cycle boundary (an exception is logged and never fails the cycle), Storage.record_health classifies every active source: a changed health clears kept_health when it differs from the new health (a keep answers one state; any change ends it), and each change is logged with obs_log('source.health', source_id, old, new) and a console line.

5. Operator actions. Storage.keep_source sets kept_health = health and kept_at, refusing a source that is not flagged; Storage.unkeep_source clears both. API: PATCH /api/sources/{id}/keep and PATCH /api/sources/{id}/unkeep beside pause and resume (api.py line 815), a 400 for a source with nothing to keep, a 404 for an unknown id. A URL change through Storage.update_source (storage.py line 1346) is a fix: when url is among the updated columns it also resets error_count, last_error, next_fetch_at, entries_served, newest_item_at, health, kept_health and kept_at, so the new URL is fetched next cycle and judged afresh; a name or naughty change resets nothing. resume_source also clears next_fetch_at. Remove is unchanged.

6. API read. SourceResponse (api_models.py line 76) gains, additively, health, attention (bool), entries_served, newest_item_at, next_fetch_at, kept_health, kept_at, created_at; _source_row_to_dict (storage.py line 140), the one mapper both source readers share, carries them; the source routes fill them from the row. No new read route: GET /api/sources/health is #112's.

7. TUI. db.Source gains the same fields; GetSourcesWithCounts (tui/internal/db/queries.go line 348) selects them and, on a database that predates them (a TUI upgraded before the daemon restarted), falls back to the old select with no health, as LatestDriftCheck does for a missing table; fetchSourcesRemote maps them from the API. The main-screen line follows the drift path: the item reload that reads drift (model.go line 1291) also reads the sources needing attention (local: SELECT health, COUNT(*) FROM sources WHERE attention = 1 GROUP BY health, tolerating the same old schema; remote: GET /api/sources filtered on attention), and RenderList (feed.go line 146) puts sourcesWarningText after driftWarningText on the header line: '⚠ Sources: 1 broken, 2 empty, 5 dormant', only nonzero states, in that order, and nothing when none. formatSourceLine (model.go line 1790) and SourceModal.renderListContentOnly (source_modal.go line 482) drop their own rules (ErrorCount > 3, 24 hours) for one status mark read from health and attention: paused, unclassified, healthy, broken, empty, dormant, kept. The sources screen shows under every source with attention, or with failures, or kept, one evidence line: broken and failing 'N failures · <last error> · next try <time> · last success <date or never>', empty 'served 0 entries · <last fetched>', dormant 'newest item <date>' or 'nothing dated since added <date>', kept 'kept (<state>) since <date>'. The last error passes through one helper that strips C0 and C1 controls, ESC and DEL and flattens it to one line before it is rendered. K on the sources screen keeps a flagged source and unkeeps a kept one, through new operations calling the API like PauseSource does (operations/sources.go line 117); the help line names it.

8. CLI. format_source_row (cli/src/cli/source.py line 56) gains a Health column showing the stored health, with ' (kept)' when kept_health equals it; `prismis-cli source keep <id>` and `prismis-cli source unkeep <id>` call the two routes.

Acts on the cause: The cause is that a fetch is recorded only as a failure counter that, at five, writes the operator's pause flag, and nothing records what a successful fetch served. The form deletes that write, so the daemon can no longer produce the rule-paused state, and records every fetch's served count, newest entry time, attempt and next-due times and the classification judged from them in the sources row, so broken, empty, dormant, kept and paused are distinct stored states that every client reads instead of guessing from error_count.

## Commitments

- The daemon never writes active; the five-strike UPDATE is deleted, and the one source it switched off on the operator's host comes back under backoff and shows broken.
- A failing source's next fetch waits fetch_interval x 2^(n-1) after its nth consecutive failure, capped at 1440 minutes, landing on the cycle nearest that time; one successful fetch returns it to every cycle.
- A source is broken at the failure whose backoff wait first reaches the daily cap, computed from the fetch interval; before that its failures are evidence only.
- Empty means the last successful fetch served zero entries; dormant means the newest item the daemon has seen is more than 90 days old, or nothing dated has been seen in the source's first 90 days; both read what the fetch served before the pipeline's own filters, so empty and quiet differ.
- Health, its evidence and the warning flag live in the sources row; the warning rule is one trigger in the schema; the TUI, CLI and API read those columns and judge nothing themselves.
- The main screen carries one sources line beside the drift line, in local and remote mode, present exactly while a source has attention.
- Keep answers one state: any change of health ends it, and a source that returns to healthy on its own clears its warning.
- Fix is a URL change, which resets the source's fetch record so the new URL is judged afresh; keep and unkeep are one API route each, called by the TUI's K and the CLI.
- Every change is additive: new columns with defaults, new response fields, new routes; old clients keep reading sources unchanged, and a new TUI reads an old database without failing.
- Error text the sources screen shows is stripped of terminal controls and flattened to one line.

## Sacrifices

- The stored evidence is each source's latest state, not a per-fetch history; a history of what was tried is left to #112's record. (not a case: What the stored record holds is a property of the design, not a case a use of prismis runs into; #112 owns history.)
- A retry lands on the cycle nearest its due time, so a wait can run up to half a fetch interval short of or past fetch_interval x 2^(n-1), and past the daily cap by under half an interval when the interval does not divide a day. (0 of 1 the operator's daemon host configuration)
- A YouTube channel whose discovery returns nothing reports no served count, so a YouTube source is never classified empty, and its newest video beyond the lookback is unknown, so its dormancy rests on items stored and its age. (12 of 49 sources on the operator's daemon host, grouped by type (youtube active 12))
- A source failing below the broken threshold raises no main-screen line, so a dead site at the operator's 120-minute interval is announced at its fifth failure, 30 hours after the first (waits of 2, 4, 8 and 16 hours between them), not at once. (0 of 48 active sources on the operator's daemon host carrying any consecutive failure (the query's error_count > 0 rows that are active))
- The migration turns back on the sources the five-strike rule switched off without asking the operator first; the main-screen line is how they learn of it. (1 of 49 sources on the operator's daemon host with active = 0 and error_count >= 5)
- A manual --once run honours backoff, so it does not fetch a source still waiting; pause then resume, or a URL change, clears the wait and retries at the next cycle. (0 of 48 active sources on the operator's daemon host that would be waiting in backoff today (active with error_count > 0))

## Risk

If classification misreads a fetch, the main screen shows a false warning or misses a true one; the operator can keep a false one, and nothing is switched off or deleted, so the worst case is noise or a missed signal, never lost data. If the backoff due check is wrong, a failing source is fetched every cycle (today's cost) or waits longer than a day (a recovered site picked up late); both are bounded and visible in next_fetch_at. If the migration's reactivation matched a row the operator had paused, that source would be fetched again until paused again; the host measurement shows no such row.
